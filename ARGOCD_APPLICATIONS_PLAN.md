# ArgoCD Applications Plan

## Problem

The whole cluster is one ArgoCD Application, `lab`
(`cluster/manifests/lab/lab-application.yaml`): 538 manifests, 23
namespaces, rendered by `just render-lab` (`tk export` of
`environments/lab`) into one flat directory. Sync, health, hooks and
auto-sync are per-Application, so:

- One service's failing hook or Degraded resource fails the sync for every
  service. A broken Forgejo PreSync gate blocked every ArgoCD sync for 9 days.
- Upgrade gates (`forgejo-dump-gate`, `immich-db-upgrade-gate`,
  `pinepods-db-upgrade-gate`, `miniflux-db-upgrade-gate`) can each stop the
  whole cluster.
- Pausing auto-sync for one service (upgrade lock, restore) pauses
  everything.
- SyncFail hooks cannot tell which service failed.

`FORGEJO_MIGRATION_PLAN.md` → Forgejo Upgrades depends on Forgejo being its
own Application.

## Target

One Application per service. The 15 services are generated by an
**ApplicationSet** with a git directory generator over
`cluster/manifests/<namespace>/` — ArgoCD's recommended pattern ("Our
recommendation is to look at ApplicationSets", Cluster Bootstrapping docs);
the 7 operator Applications are ordered by sync waves in the `argocd`
Application (step 3). No separate root Application: `argocd` is the
parent.

**ArgoCD manages itself (decided)** — the layout of argoproj-labs'
argocd-autopilot (`cmd/commands/repo.go:583-650`) minus its
`autopilot-bootstrap`/`root` layers, which carry projects and multi-cluster
features this repo does not use:

- `cluster/manifests/argocd/` holds the ArgoCD chart, a plain `argocd`
  Application whose source is `cluster/manifests/argocd/` (self-managing, as
  `lab` does today and autopilot's `argo-cd` app does), the 7 operator
  Applications and the ApplicationSet.
- The `argocd` Application has **no finalizer** (autopilot `noFinalizer:
  true`; vehagn/homelab's `infrastructure` ApplicationSet, which generates its
  ArgoCD app, likewise): deleting the app never deletes ArgoCD. Today's `lab`
  has none either (`environments/lab/main.jsonnet:484-512`).
- The `argocd` Namespace carries `argocd.argoproj.io/sync-options:
  Prune=false` (autopilot, `pkg/kube/kube.go:167`).
- The ApplicationSet: git directory generator over `cluster/manifests/*`
  with `cluster/manifests/argocd` and the 7 operator directories (step 3)
  excluded, generating the 15 service apps.
  Template: `resources-finalizer.argocd.argoproj.io` on each app, so removing
  `cluster/manifests/<namespace>/` deletes that service's resources
  (autopilot's workload ApplicationSets: `prune: true`,
  `preserveResourcesOnDeletion: false`, `cmd/commands/project.go:298-299`);
  `project: default`, automated sync with `prune` + `selfHeal` and
  `syncOptions: [ServerSideApply=true]`, as `lab` today (ArgoCD's
  self-management docs require server-side apply);
  `ignoreApplicationDifferences: [{jsonPointers:
  [/spec/syncPolicy/automated/enabled]}]` so a single app can be paused
  (Forgejo upgrade lock, restores) without the controller reverting it. The
  docs' auto-sync example ignores all of `/spec/syncPolicy`, but the
  controller strips ignored paths from both the live and the generated
  Application before its merge patch
  (`applicationset/utils/createOrUpdate.go:186-256`), so that would freeze
  every syncPolicy field (`prune`, `selfHeal`, `syncOptions`, `retry`) at
  each app's creation and let template changes silently miss the existing
  apps. The narrow pointer strips only the scalar the lock sets; it sits in
  an object, so the docs' list-replacement caveat does not apply.
- No extra guard on the ApplicationSet object itself (neither autopilot nor
  the surveyed homelab repos add one): removing it takes a deliberate edit
  to `main.jsonnet`, since `render-lab` swaps atomically
  (`cluster/Justfile:8-16`).
- Source: one jsonnet value used by the `argocd` Application, the operator
  Applications and the ApplicationSet's generator and template. At cut-over
  it is today's `https://github.com/ftzm/dots.git`, `targetRevision: HEAD`
  (`environments/lab/main.jsonnet:494-495`); `FORGEJO_MIGRATION_PLAN.md`
  step 3 (Flip) changes that one value to the nas mirror (Decisions).

2. **Render per namespace (decided): Tanka inline environments.**
   `environments/lab/main.jsonnet` returns one `tanka.dev/v1alpha1`
   `Environment` per app (Tanka's documented way to define several
   environments in one file); today's file becomes `lab.jsonnet`, imported
   unchanged, and the new `main.jsonnet` maps each top-level key to its
   namespace's environment (`observability` → `monitoring`), with an
   `assert` failing the render on an unmapped key. Export:
   `tk export <tmp> environments/lab --recursive --format
   '{{env.metadata.name}}/{{.metadata.name}}-{{.kind | lower}}'
   --skip-manifest`. Prototyped on a scratch copy of `cluster/` (2026-10-01,
   tk v0.36.1, before `e6085198` added `external-dns`): 22 directories, 509
   files, all byte-identical to `manifests/lab` — the cut-over is a pure
   path change, as step 4 assumes.
   Forced constraints:
   - `environments/lab/spec.json` is deleted: with it present, Tanka treats
     the file as one static environment and exports the `Environment`
     objects themselves as resources.
   - Every environment keeps `spec.namespace: 'default'`: Tanka injects
     `spec.namespace` into objects without one unless it knows the kind is
     cluster-scoped, which today puts `namespace: default` on the
     `letsencrypt` ClusterIssuer, both `ClusterImageCatalog`s and the
     `traefik` IngressClass; a per-app namespace changed those 4 files.

   Consumers:
   - `just render-lab` (name kept — `renovate.jsonnet:107`, `ci.yml:42`
     and the triage prompt call it): recursive export into a temp dir
     outside `manifests/`; each `secrets/*.enc.yaml` copied into
     `<tmp>/<its metadata.namespace>/`, failing if that directory does not
     exist; then all of `manifests/` swapped atomically, as `manifests/lab`
     is today (`cluster/Justfile:8-16`).
   - `just diff-lab`: `tk diff environments/lab` fails with several inline
     environments ("found multiple Environments … Use `--name`"), so it runs
     `tk diff --name <namespace>` per `manifests/` directory.
   - `just test-rules`: globs `manifests/*/*-prometheusrule.yaml` and
     `manifests/*/loki-rule-*-configmap.yaml`. Basenames are unique across
     the 530 files, so `tests/.rules/` and the `*.test.yaml` `rule_files`
     are unchanged.
   - The `render-lab` flake check and Renovate's `postUpgradeTasks`
     (`FORGEJO_MIGRATION_PLAN.md`): `cluster/manifests` in place of
     `cluster/manifests/lab`.
   - `cluster/README.md` (required by `cluster/CLAUDE.md` after any
     change): every `manifests/lab/` reference (`:87`, `:102`, `:107`,
     `:117`, `:183`, `:211`, `:395`, `:428`) and the hook
     descriptions (`:580` postgres gates, `:659` `forgejoDumpGate`; step 7).

   Rejected: one Tanka environment per directory — splitting the
   3004-line `main.jsonnet` and its shared helpers for the same output.
3. **Ordering between apps (decided): app-of-apps sync waves with the
   Application health check**, ArgoCD's documented mechanism — the stable
   Resource Health docs restore the `argoproj.io/Application` health check
   for those "using app-of-apps pattern and orchestrating synchronization
   using sync waves" (opt-in since 1.8, argoproj/argo-cd#3781: a child's
   health no longer bubbles to its parent by default). The hybrid of
   mitchross/talos-argocd-proxmox: dependencies as ordered Applications
   under the parent, the ApplicationSet in a later wave.
   - Why ordering is needed (fresh cluster only): 55 CRDs come from 6
     operator apps (`traefik` 25, `monitoring` 11, `cnpg-system` 11,
     `cert-manager` 6, `sealed-secrets` 1, `sops-operator` 1; the `nfs`
     StorageClass from `nfs-provisioner`), and admission webhooks with `failurePolicy: Fail` need
     their pods Ready — cnpg (`clusters`, `databases`, `backups`,
     `scheduledbackups`, `poolers`) and cert-manager (`cert-manager.io`
     `*/*`, so traefik's `Certificate`); kube-prometheus-stack's are
     `Ignore`. The operator apps depend on each other too (checked over
     every non-core `apiVersion` in their manifests): `cert-manager`'s
     SopsSecret `cloudflare-api-token` needs `sops-operator`; `traefik`'s
     `Certificate` needs cert-manager's CRD and webhook; `monitoring`'s
     SealedSecret `grafana-admin` needs `sealed-secrets`, its IngressRoutes
     `grafana` and `loki` need `traefik`; `traefik`'s PodMonitor needs
     `monitoring` — a cycle, broken by moving that PodMonitor to the
     `monitoring` app (step 1); the `argocd` app's `IngressRouteTCP` needs
     `traefik`, its ServiceMonitors and PrometheusRule `monitoring`. Within
     `cert-manager`, the `letsencrypt` ClusterIssuer passes through the
     app's own webhook (cluster-scoped, so the webhook's `namespaceSelector`
     does not exempt it) and carries `sync-wave: "1"`, after the webhook
     Deployment is Healthy. Rejected for the cycle:
     `SkipDryRunOnMissingResource` on the cross edges, which makes a fresh
     bootstrap depend on retry timing. A missing CRD fails the dry-run, which fails the sync without
     hooks or SyncFail (gitops-engine `pkg/sync/sync_context.go:455-458`);
     auto-sync then does not retry that SHA (`controller/appcontroller.go:2381-2385`,
     checked before `selfHeal`).
   - Rejected: waves on ApplicationSet-generated Applications (no effect —
     "the ApplicationSet controller creates all Applications at once",
     mortennordbye/homelab docs); Progressive Syncs ("RollingSync will force
     all generated Applications to have autosync disabled" — defeats
     automated sync and the per-app Forgejo lock); a long `retry` in the
     template (khuedoan/homelab: limit 10, backoff 1m ×2, max 16m) — retry
     applies to every failed sync and holds it in `Running` ("Retrying
     attempt #n") until exhausted, so a real failure would go unreported for
     up to ~2 h.
   - Waves in the `argocd` Application:

     | Wave | Contents |
     |---|---|
     | `0` | the ArgoCD install |
     | `1` | Applications `sealed-secrets`, `sops-operator`, `cnpg-system`, `nfs-provisioner` |
     | `2` | Application `cert-manager` (its SopsSecret needs `sops-operator`) |
     | `3` | Application `traefik` (its `Certificate` needs cert-manager's webhook) |
     | `4` | Application `monitoring` (needs `sealed-secrets` and `traefik`) |
     | `5` | ArgoCD's `IngressRouteTCP` (needs `traefik`), ServiceMonitors and PrometheusRule (need `monitoring`); the ApplicationSet (15 service apps) |

   - The operator Applications are emitted by jsonnet like the rest, same
     template as the ApplicationSet's (finalizer, automated sync, `prune` +
     `selfHeal`), plus their wave.
   - `resource.customizations.health.argoproj.io_Application` (the Resource
     Health docs' Lua) goes into the chart's `configs.cm`, so the parent
     waits on each wave's Applications being Healthy, not merely created.
   - Retry stays ArgoCD's default for automated syncs, `Limit: 5`
     (`appcontroller.go:2369-2373`), as `lab` has today.
   - Steady-state cost: a sync proceeds from "the first number where any
     resource is out-of-sync or unhealthy" (Sync Waves docs), so a Degraded
     operator app holds back the `argocd` app's later waves (ApplicationSet
     edits, ArgoCD's monitors) until it recovers; service apps and the
     wave-`0` install keep syncing. With the health check on, a Degraded
     operator app also shows its parent Degraded, so `ArgoCDAppDegraded`
     fires for both.
4. **Cut-over without pruning (decided).** Tracking is by annotation:
   ArgoCD `v3.5.3`, `argocd-cm` sets no `application.resourceTrackingMethod`
   (default `annotation`, Resource Tracking docs); live resources carry
   `argocd.argoproj.io/tracking-id` (`lab:apps/Deployment:forgejo/forgejo`,
   `lab:/Namespace:default/forgejo`) and no instance label;
   `application/lab` has no finalizers. Adoption, from v3.5.3 source: a new
   app finds its target objects in the cluster cache even when another app's
   tracking-id is on them (gitops-engine `GetManagedLiveObjs`,
   `pkg/cache/cluster.go:1199-1214`), raises `SharedResourceWarning`
   (`controller/state.go:804-813`), and its sync rewrites the tracking-id to
   itself — no delete, no recreate. `lab` prunes only objects whose
   tracking-id names `lab` (`controller/cache/cache.go:734-736`), so the
   only hazard is `lab` pruning before re-tracking. Sequence:
   1. Commit `prune: false` on `lab`; confirm live
      (`kubectl get application lab -o jsonpath='{.spec.syncPolicy}'`)
      before the next commit lands.
   2. Commit the new layout (steps 1–3, 6, 7): `manifests/argocd/` and
      `manifests/<namespace>/` added, `manifests/lab/` removed. `lab` can no
      longer render its path and cannot prune either way.

      (server-side apply of `manifests/argocd/`) — the one-time cut-over

      needs rehearsed. The `argocd` app adopts the install; the ApplicationSet
      generates the 15 service apps; the 7 operator Applications come from
      `manifests/argocd/` itself. Each app adopts its resources.
   4. Confirm no live object still carries a `lab:` tracking-id, then
      `kubectl delete application lab`: no finalizer, so non-cascading (the
      App Deletion docs: managed resources are left running).

   Rejected: a transitional `manifests/lab` through which `lab` creates the
   `argocd` Application — the `argocd` app's own directory defines the same
   object, and two `selfHeal` apps would keep rewriting its tracking-id.
   Acceptance: all 23 Applications Synced and Healthy, none with a
   `SharedResourceWarning` condition, no live object with a `lab:`
   tracking-id, `application/lab` gone.

## Hooks and waves (decided)

**No hook depends on another service.** Every hook Job uses only objects of
its own namespace, emitted by its own key, and sets no ServiceAccount:

| Hook | Uses |
|---|---|
| `forgejo-dump-gate` (PreSync) | PVCs `forgejo-data`, `forgejo-backup`; Service `forgejo` |
| `immich-db-upgrade-gate` (PreSync), `-finalize`, `-vchord-reindex` (PostSync) | PVC `immich-db-backup`; Service `immich-database-rw`; Secret `immich-database-app` (cnpg, from Cluster `immich-database`) |
| `miniflux-db-upgrade-gate` / `-finalize` | PVC `miniflux-db-backup`; `miniflux-database-rw`; `miniflux-database-app` |
| `pinepods-db-upgrade-gate` / `-finalize` | PVC `pinepods-db-backup`; `pinepods-database-rw`; `pinepods-database-superuser` |

**Cut-over re-runs them harmlessly.** Each adopting app's first sync runs its
hooks; the last runs (kept by `BeforeHookCreation`) show the no-op path: the
DB gates "PostgreSQL major 18 matches target, extension matches image - no
upgrade pending", the finalizers "PostgreSQL major unchanged (18) - nothing
to finalize", forgejo "forgejo 16.0.5 already matches the image - no upgrade
pending"; `immich-db-vchord-reindex` rebuilds only an index that fails to
read.

**PreSync gates cannot complete on a fresh cluster** — today in `lab` and
after the split alike. gitops-engine runs every PreSync task before any
Sync-phase task (`pkg/sync/sync_context.go:564-574`; non-hook resources are
Sync phase, `:791-792`), so the gates' PVCs do not exist when their Jobs are
created and the pods never schedule; the DB gates would also wait on a
`*-database-rw` Service whose `Cluster` is itself Sync phase. ArgoCD has no
phase that applies resources before PreSync (argoproj/argo-cd#9891, open)
and "cannot know if it is running a first-time 'install' or an 'upgrade'"
(Helm docs), so the gate must handle a fresh install itself.

**Layout — Sync hooks in an intermediate wave**, the workaround of
argoproj/argo-cd discussion #9801 ("simulate PreSync hooks between waves
using Sync hooks in an intermediate wave"), for `forgejo`, `immich`,
`miniflux`, `pinepods`:

| Wave | Contents |
|---|---|
| `-1` | the gate's PVCs and their static PVs; the gate, `argocd.argoproj.io/hook: Sync` |
| `0` (default) | everything else, Deployments and the cnpg `Cluster` included |
| PostSync | finalize / vchord-reindex, unchanged |

- Gating holds: a running hook holds back the next wave and a failed task
  fails the sync before later waves (`sync_context.go:494-500`,
  `:540-543`); SyncFail hooks run on any failed task, whatever its phase
  (`setOperationFailed`, `:745-754`).
- The PVCs share the gate's wave, not an earlier one: a multi-step wave
  completes only when its resources are healthy (`:497`), a Pending PVC is
  `Progressing` (`pkg/health/health_pvc.go:33-34`), and `forgejo-data` is
  `local-path`, `WaitForFirstConsumer` — Pending until a pod mounts it, and
  the gate is that pod. (The `*-backup` PVCs bind static PVs; `nfs` is
  `Immediate`.)
- Fresh-install detection: forgejo — no `/data/gitea/gitea.db` → exit 0
  (`FORGEJO_MIGRATION_PLAN.md` → Forgejo Upgrades). DB gates — the
  `Cluster` object absent (API GET on `clusters.postgresql.cnpg.io/<name>`
  → 404) → exit 0, through a per-namespace ServiceAccount + Role with `get`
  on that one resource (the gate images have `python3` but no `curl`,
  `wget` or `kubectl`: Execution tasks, 5). Not psql (cannot tell "no database" from "database
  down"), not a marker on the backup PVC (static NFS PVs outlive the
  cluster), not DNS on `*-database-rw` (a CoreDNS outage would read as
  fresh and skip the pre-upgrade dump). With the `Cluster` present, the
  current wait-then-check logic runs unchanged.

## Sequencing (decided)
